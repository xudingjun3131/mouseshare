## v0.5.1 —— 修用户实测报的 3 个 bug

用户实测 v0.5.0 后反馈：
1. **窗口缩小/隐藏后卡顿**
2. **还是会出现两个屏幕一起滑动**
3. **还是不能复制文件到另一个屏幕**

### Bug 1+2 共同根因：macOS App Nap（最重要）

- 窗口不可见 → macOS 把进程当 idle → 合并定时器 + 判定 event tap 不活跃 → 送 `TapDisabledByTimeout`。
- tap 被禁用期间：callback 不跑，**本地事件直接进系统**（本地光标动）；tap 重新 arm 后我们仍在 `Forwarding`，又开始 drop+forward → **一鼠双光标**。这就是"卡顿"和"一起滑动"是同一个病。
- **修复**：`capture::disable_app_nap()`，用 `NSProcessInfo beginActivityWithOptions:reason:`（options = `NSActivityUserInitiated | NSActivityIdleSystemSleepDisabled | NSActivityLatencyCritical`），token 存进 `static OnceLock<usize>` 永久持有（**丢了 token = activity 结束 = App Nap 回来**）。必须在 `main()` 建窗口之前调用。
- 项目里**此前完全没有 App Nap 防护**，只有 capture.rs 的注释心虚地提了一句 "or App Nap kicked in"。

### Bug 1+2 第二根因：event-tap 线程里 lock 了 layout

- `return_control()` / `cycle_control()` 都有 `ctx.layout.lock()`，而它俩**都在 event-tap 线程上跑**（tap 被禁用时 callback 调 return_control；hotkey 也在 callback 里检测）。
- 上次会话已经为 `on_capture` 修过这个（改用 `layout_snap`），但这两个函数漏了 → 阻塞 → tap 再次超时 → **恶性循环**，短暂 hiccup 变成持续卡顿。
- **修复**：两个函数都改成 `let snap = c.layout_snap.clone();`。`leave_forwarding` 只用到 `l.local_bbox()`（本地屏包围盒），snap 里有，够用。
- **教训**：凡是能从 event-tap callback 触达的调用链，整条链都禁止 lock `ctx.layout`。加新函数时务必检查。

### Bug 3 根因：剪贴板"文本 vs 文件"两条分支互相打架

- `clipboard.rs` 的 monitor 把 text 和 files 当**两个独立通道**分别比较。
- 但一次粘贴是**一个 pasteboard 状态、多种表示**：Finder 复制文件会同时写 `public.file-url` **和** 纯文本（文件名）。
- 于是死循环：text 分支命中 → `st.files.clear()` → 广播文件名文本；file 分支发现 files "变了" → `st.text = None` → 发文件；下一轮 text 又命中……**每 200ms 交替**。
- 用户看到的现象：远端剪贴板在「文件」和字符串 `"report.pdf"` 之间反复横跳，**粘贴大概率落到文本形式** → 表现为"不能复制文件"。同时机器一直在重编 base64 + 重传 → 也是卡顿来源之一。
- **修复**：一次快照同时读 text + files，**文件优先**；命中文件时把随附的 text 一并记进 `st.text`，让 text 分支无法把它当成新复制。

### Bug 3 第二根因：macOS 只读了一种 pasteboard 表示

- 原来 `read_files()` 只走 `pasteboardItems` + `public.file-url`。只写旧式 `NSFilenamesPboardType` 的 app 复制的文件**完全不可见**。
- **修复**：三级 fallback —— ① `pasteboardItems` 的 `public.file-url` ② pasteboard 上直接的 `stringForType:public.file-url` ③ `propertyListForType:NSFilenamesPboardType`（NSArray<NSString> 绝对路径）。
- `write_files()` 也补写 `NSFilenamesPboardType`，**必须在 `writeObjects:` 之后**（它会 clearContents，写前面会被清掉）。

### 顺带修的两个真实缺陷

- **transfer manifest 与内容不一致**：原来先造 manifest 再开文件，某个文件 `File::open` 失败 → 接收端还在等它的字节 → **后面所有文件内容全错位**。改为先 `open` 全部文件，manifest 只由真正打开成功的生成。
- **`finish()` 不校验**：传输损坏时把不存在的路径写进剪贴板 → Cmd+V 静默失败。现在 `.filter(|p| p.exists())`。
- **`begin()` 误删并发传输**：原来清掉"所有非本次"的目录；改成只清修改时间 > 30min 的。
- **`send_paths` 长时间持 `net` 锁**：整个文件读取+发送期间持有，而 tap callback 也要这把锁 → 传大文件 = 阻塞输入 = tap 超时。改成每条消息单独 lock。
- **`pump_writes` 合并 motion**：把连续 MouseMotion 累加成一帧。位移总量没错，但接收端执行的**光标更新次数变少** → 变成"大步跳"，这正是"远端光标不跟手"。改为**只批量 syscall、不合并内容**。

- `cargo check --target x86_64-pc-windows-gnu` 0 error。

## v0.5.3 (10:44) — 双鼠(窗口隐藏后加重) + Mac→Win 文件单向

**Bug 1 双鼠**（窗口最小化后加重）：
- **根因**：macOS 事件 tap 回调里每帧 `ctx.net.lock().unwrap()` 转发鼠标移动。任何对该锁的等待都让 tap 变慢 → macOS 判 unresponsive → `TapDisabledByTimeout` 禁用 tap → 禁用期间本地事件不被 Drop（本地光标动）而 mode 仍是 Forwarding（远端还在动）= 双鼠。窗口隐藏时 App Nap 拖慢全进程、放大锁窗口。
- **修复**：转发输入改走**无界 mpsc channel**（`GrabCtx.input_tx`），tap 回调只做无锁 `send`，一个 pump 线程拿 net 锁真正发送。`leave_forwarding` 的 held key/button 释放同样入队。`TapDisabledByTimeout` 分支改 `try_lock`（新增 `try_return_control`），绝不阻塞。
- **架构教训**：**event-tap 回调里绝不允许 lock 任何可能被别处长时间持有的锁**。高频输入路径必须 lock-free（channel 队列），低频（跨屏瞬间）才可容忍短锁。这是本项目第二次踩这个坑（上次是 layout 锁）。

**Bug 2 Mac→Win 文件单向**：
- **根因 1（确定）**：monitor 用 `st.files != files` **比内容**判断变更。复制同一个文件两次 → 路径相同 → 判"没变" → 第二次静默跳过。用户重试永远失败。
- **修复**：改读 OS 剪贴板 generation 计数器（macOS `NSPasteboard.changeCount` / Windows `GetClipboardSequenceNumber`），每次写入必增，内容相同也能检测。`ClipState` 加 `gen` 字段，`apply_remote_*` 写入后回读 gen 防回环。
- **根因 2（未完全定位）**：接收端无诊断，失败静默。已加 `FILE-RECV-BEGIN` / `FILE-RECV-FIRST-CHUNK` / `FILE-RECV-END` 日志，下次可直接定位 read/send/reassemble/pasteboard-write 哪段断。
- **待验证**：若 Mac→Win 仍失败，看 diag 日志 —— Mac 端无 `CLIP-FILES-DETECTED` = read_files 读不到；Mac 有但 Win 无 `FILE-RECV-BEGIN` = 网络/发送；Win 有 BEGIN 无 END = 重组失败。diag 日志路径见 `diag::log_path()`。

tag v0.5.3 = c926636，已 push。

## v0.6.0 (14:05) — 四个 bug 的真正根因

用户报告 v0.5.3 四个 bug 全部未修复。逐文件通读后找到确定性根因：

1. **App Nap 从未真正禁用**（隐藏窗口卡顿/无法跨屏/双鼠的 Mac 端总根因）：`disable_app_nap()` 把 `beginActivityWithOptions` 包在 autoreleasepool 里，但该 selector 返回 **autoreleased** token（非 alloc/new/copy 命名），pool drain = 函数返回时就释放了 token → 活动立刻结束 → App Nap 照常。修复：显式 `retain` 后存 static，永不释放；CI 的 Info.plist 加 `NSAppSleepDisabled=YES` 双保险。
2. **热路径仍有 net 锁**：Forwarding 分支每帧 `net.lock().has_peer()`，pump 线程每帧也拿同一把锁 → tap 等锁被禁。改 `try_lock`（busy 视为存活直接转发）。`TapDisabledByUserInput` 也补了 `try_return_control`（原来只 show_cursor，Forwarding 状态残留 → 双鼠）。
3. **Mac→Win 文件复制可观测性 + relay 缺口**：hub 不把 secondary 发来的文件消息 relay 给其他 peer（加 `broadcast_all_except`）；发送端无任何提示（加 toast「已发送 n 个文件」）。若仍失败，看两端 diag 日志：Mac 无 `CLIP-FILES-DETECTED`=读不到；Mac 有 Win 无 `FILE-RECV-BEGIN`=网络；Win 有 BEGIN 无 END=重组；有 `FILE-APPLY-FAILED`=CF_HDROP 写入失败。
4. **Ctrl+Alt+Space 热键在 Mac 上从未生效**：macOS 修饰键只发 FlagsChanged 不发 KeyDown/KeyUp，`hk.ctrl/alt` 永远 false。tap 现在读 `cg_ev.get_flags()` → 新 `RawInput::Mods{ctrl,alt}` → on_capture 更新热键状态。Win 端 rdev 有 KeyPress 不受影响。
5. **测试死锁新教训（重大）**：结构体字面量里 `Ctrl { local_bbox: pla.lock().unwrap().local_bbox(), layout_snap: pla.lock().unwrap().clone() }` —— **第一个字段的临时 MutexGuard 存活到整个字面量求值结束**，第二个 lock 同线程重入同一 mutex → 所有集成测试永久挂死（CPU 0.02s、sample 显示"无人持锁"极具迷惑性，持有者就是等待者自己）。必须用 `{ let g = ...; }` 块作用域提前 drop guard。曾用 v0.5.3 二进制对照实验确认是本次改动引入。

v0.6.0 = 41964f2，tag 已 push。**重要提醒给用户**：语言按钮在 v0.5.2+ 已移到 sidebar 左下角；若仍觉得被遮挡，先确认 UI 左上角版本号 ≥ 0.6.0（旧版残留可能性大）。

## v0.6.1 (15:30) — 语言按钮"点不动"的完整排查 + 两个真修复

用户再次报"mac 上中英文切换点击不了"。这次做了完整的实证排查（合成 CGEvent 点击 + 截图 + diag 插桩 + 对照实验），结论：

**已证实的真 bug（已修）**：
1. **CGEventTap mask 溢出**：`events_of_interest` 含 `TapDisabledByTimeout`(0xFFFFFFFF)/`TapDisabledByUserInput`(0xFFFFFFFE)，`CGEventMaskBit!` 做 `1u64 << event_type`。**debug 版必 panic**（capture 线程秒死，dev build 完全无法捕获——这就是之前 debug 版"没有 capture 日志"的原因），release 版走 UB（arm64 上恰好回绕成 bit62/63，侥幸无害）。这两个是伪事件**不可 mask**，macOS 无论 mask 都会投递给回调，本来就不该放进列表。修复 = 直接删掉这两项。
2. **转发期间自己的 UI 被点死**（用户报告的真正体验根因）：转发（cursor 在 Win 侧）时所有本地点击被吞/转发——14:19 用户发消息前 diag 日志有 11 次 HAND-OFF/RETURN 循环，用户在 flapping 风暴里点语言按钮当然永远无效。修复：`GrabCtx.ui_window_rect`（GUI 每帧发布窗口屏幕矩形），tap 回调里 ButtonDown 落在窗口内 → leave_forwarding + 本地投递（ShareMouse 同款行为）。注意 leave_forwarding 已会释放 held buttons，不要再手动补发 MouseUp（会造出远端幽灵点击）。

**已排除的嫌疑（重要排查结论，勿重查）**：
- 按钮代码（bottom_up + allocate_exact_size + Sense::click）与 egui 0.31 无关，最小复现 app 三按钮全通。
- 安装版 /Applications 的二进制 = CI v0.6.0 = dmg 三方 hash 一致，非旧版残留。
- Info.plist 缺 NSHighResolutionCapable 不影响（截图清晰 2x 渲染，hover 1:1 正确高亮）。
- corrupt mask 在本地 release 下点击也全通过 → mask 不是安装版吞点击的直接原因。
- **合成点击测试不可靠**：egui 判定 click 要求按住期间位移 ≤6px（`max_click_dist`）。用户真实鼠标在机器上活动时，合成按住 40-100ms 会被叠加漂移 >6px → egui 判为 drag。合成点击"失败"多半是这个 + 首击激活窗口被吃。验证 UI 点击务必用 hover 高亮截图（`screencapture -C`）或让用户真点。quarantine 的下载二进制会秒退（先 `xattr -cr`）。
- 判定点击是否到达 egui：watch `pointer.any_down()`；`hovered=false` 而 pointer 在 rect 内 = 按压被别处认领或已判 drag。

**诊断方法论**：给 lang_toggle_btn 和 tap 回调加 diag 临时日志 + swift 脚本合成点击（CGEvent post cghidEventTap）是最有效的实证组合；pkill 杀旧实例、System Events 查窗口位置、`osascript set frontmost` 置前。

## 右上角"中英文切换按钮被遮挡"的真正根因（16:20）

用户截图红框圈出窗口右上角一个青色药丸（实为 toolbar 里的连接状态 pill「主机（正在服务）」，不是语言按钮）。逐像素分析截图 + 读 eframe/winit 源码定位到**真正的根因**：

- **根因**：`main.rs` 建窗口用了 `.with_fullsize_content_view(true)` + `.with_title_shown(false)`，但**漏了 `.with_titlebar_shown(false)`**。egui 0.31 里 `titlebar_shown=false` 才映射到 winit 的 `titlebar_transparent`（→ `NSWindow.titlebarAppearsTransparent`）。缺失时 macOS 画一条**不透明**标题栏（浅色模式白色，约 28pt 高）盖在窗口内容顶部，正好把 toolbar 右上角的 pill 裁掉只剩底部一条。
- **修复（main.rs 一行）**：macOS viewport 追加 `.with_titlebar_shown(false)`。这样标题栏透明、内容透出（Big Sur+ unified toolbar 的标准形态），traffic lights 仍由 `.with_titlebar_buttons_shown(true)` 保持可见，toolbar 已有的 `add_space(82)` 左避让 + `inner_margin right/top` 让位仍有效。
- **关键映射**（egui-winit lib.rs 1757-1758）：`with_titlebar_buttons_hidden(!titlebar_buttons_shown)`、`with_titlebar_transparent(!titlebar_shown)`。即 titlebar_shown 默认 true → 不透明；要透明必须显式传 false。
- **教训**：截图不要只看整体，`PIL` 逐列扫描像素颜色 + 画红框 bbox 能精确量出被裁的高度（pill 只露出 15px/22px），比肉眼判断可靠。eframe 的 ViewportBuilder 字段在 egui-0.31.1/src/viewport.rs（`titlebar_shown` 等 macOS 字段都在那里），grep 因文件编码偶发查不到，必要时直接 Read 文件。
