## mouseshare (cross-platform LAN KVM)
Built from scratch a Rust app that shares mouse/keyboard/clipboard across Win/Linux/Mac over LAN, with a draggable screen-layout GUI.

Stack: `rdev` (capture via `listen` + inject via `simulate`, enable `serialize` feature to forward keys), `arboard` (clipboard), `eframe`/`egui` (GUI), plain TCP length-prefixed JSON protocol.
Topology: one Primary (hub) captures real input and forwards to neighbour screens; Secondaries connect and inject. Edge crossing uses a "treadmill" warp (when cursor hits a screen edge and keeps moving, warp it to the opposite edge so the unbounded virtual cursor continues onto the neighbour).
CI: `.github/workflows/build.yml` builds Win (.exe + Inno Setup), Linux (.deb + tar.gz), Mac (.dmg) and attaches to a `v*` release.
Pushed to `git@github.com:xudingjun3131/mouseshare.git` (origin already configured). Debug build links on macOS.

Gotchas fixed: `eframe::run_native` closure must return `Result<Box<dyn App>, Box<dyn Error+Send+Sync>>` and its error is NOT Send+Sync, so don't use `?` into `anyhow::Result` — handle with `if let Err`. `rdev::Button::Unknown` is `u8` (not u32).

## Feature: unlimited clients + copy (commit d4f0ade, release v0.2.0)
User asked: "带复制功能，不限制客户端数量".
- 不限制客户端数量: network layer already uses unbounded `HashMap` + `listener.incoming()` loop, but a connected secondary was only usable if a matching `Screen` existed in the layout. ## Fix: macOS dmg install + mouse icon (v0.3.0, commit 54aa267)
User: "mac上这个dmg无法安装啊。没有拖拽到application的，只有一个图标，图标自行找一下鼠标的logo打上。修复打tag".
- Root cause: workflow did `hdiutil -srcfolder MouseShare.app` → dmg contained ONLY the .app (no /Applications shortcut), so nothing to drag onto; and .app had no icon (no CFBundleIconFile / AppIcon.icns) → generic icon in Finder.
- Fix in `.github/workflows/build.yml` macOS step: generate mouse logo via ImageGen → `resources/mouse-logo.png` (1024) → `sips`+`iconutil` → `resources/AppIcon.icns` (committed so CI reuses). Package step now copies icns into `MouseShare.app/Contents/Resources`, sets `CFBundleIconFile=AppIcon`, reads version from `${GITHUB_REF_NAME#v}` (default 0.0.0-dev on main push), `codesign --force --deep --sign -` (ad-hoc, so right-click→Open passes Gatekeeper), and builds dmg from a staging dir containing the .app + `ln -s /Applications Applications` (drag-to-install). Verified locally: dmg mounts with both entries, icon present, codesign valid.
- CI: run #11 (tag v0.3.0) all 3 OS green; Release v0.3.0 published with the new mouseshare-mac.dmg.
- macOS bugfix v0.3.1: main() used `?` on `start_hub`/`connect_client` — when port busy or primary unreachable, the process exited silently with no window. Fixed by introducing `Net::Idle`, collecting the error into `startup_error`, and showing a red banner in the GUI. Also added a 3s `TcpStream::connect_timeout` so unreachable secondaries fail fast (was ~75s before).
- CJK font fix v0.3.2: `eframe` `default_fonts` ships ProggyClean only (ASCII) — Chinese labels rendered as tofu. Added `app::setup_fonts` that tries macOS Hiragino Sans GB/STHeiti/PingFang/CJKSymbolsFallback, Windows msyh/simsun/simhei, Linux wqy/noto-cjk, first match wins, inserted into both Proportional and Monospace fallback chains. Called from `run_native` closure before `Box::new(gui_app)` so the very first frame is correct.
- CJK font fix v0.3.3: v0.3.2's "fix" still showed tofu — root cause: **ab_glyph (egui's font parser) cannot read TTC collections**. macOS Hiragino/PingFang/STHeiti are all `.ttc`; Windows msyh/simsun are also `.ttc`. They parsed as "empty" fonts so the GUI had nothing to render CJK with. v0.3.3 **embeds `resources/NotoSansSC-Regular.otf`** (Noto Sans SC, 30890 glyphs incl. all CJK, SIL OFL, 8.3 MB) via `include_bytes!`. Setup_fonts now uses the bundled OTF first, system fonts as fallback. Binary grows from 3MB to ~14MB; dmg/exe from ~4MB to ~10MB. Worth it for cross-platform determinism.

## Fix: app opened nothing / silent exit (v0.3.1, commit 46b3844)
User: "安装dmg后根本打不开，点击后没有反应，也没有任何弹窗".
- **Root cause (code bug, not packaging)**: `main()` used `start_hub(port)?` / `connect_client(addr)?`. Any network-init failure (port 49152 already in use, or primary unreachable) made `main()` return Err → process exited immediately, GUI never created. Launched from Finder, stderr goes nowhere ⇒ "clicked it and nothing happened, no dialog". Most likely trigger in practice: an earlier instance still running holds the port, so every later click launches an instance that dies instantly.
- Fix: `Net::Idle` variant + `Net::idle()`; `main()` matches instead of `?`, records a Chinese error string, and ALWAYS opens the GUI. `MouseShareApp` gained `startup_error: Option<String>` rendered as a red `TopBottomPanel` banner. `connect_client` now uses `connect_with_timeout(3s)` via `to_socket_addrs` (a plain `TcpStream::connect` to an unreachable LAN IP blocks ~75s with no window).
- Verified locally: 2nd instance with port conflict stays ALIVE and logs "无法监听端口 49152（Address already in use）"; secondary with unreachable host fails in ~3s and still opens.
- Also added README 排障 section (port busy, Gatekeeper right-click→Open / `xattr -dr com.apple.quarantine`, accessibility permission).
- CI: run for 46b3844 → all 6 check runs (push+tag × 3 OS) success; Release v0.3.1 published.
- Diagnostic notes: Gatekeeper here is `assessments enabled`; `lsappinfo list` is the reliable way to confirm a bundled app truly launched as `type="Foreground"` (System Events AppleScript needs a11y perms; `screencapture` failed "could not create image from display"). WebFetch caches API responses ~15 min — append `?_=<epoch>` to bust it.
