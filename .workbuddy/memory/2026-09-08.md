## v0.3.36 —— 修复"中英文切换按钮被挡住"

用户反馈 v0.3.35 后语言切换按钮被遮住。根因：`status_pill` 用 `ui.allocate_rect(Rect::from_min_size(ui.cursor().min, ...))` **手动定位矩形**，而工具栏右侧区是 `right_to_left` 布局 —— `allocate_rect` 不遵循布局方向，且宽度用 `glyph_width('M') × 字符数` 估算（中文严重失真）。它又在语言按钮**之后**绘制（后绘制=上层），所以直接盖住了语言按钮。旧版用的是标准 `ui.label`，故无此问题。

### 修复
- `status_pill` 改为**纯布局驱动**（`egui::Frame` + `inner_margin` + 内层 `horizontal` + 两个 `label`），不用任何手动矩形；状态点改用 `allocate_exact_size` + `circle_filled` 画真圆（不依赖 "●" 字形）。宽度自动适配任意语言。
- `secondary_btn` 同步加固：`allocate_rect` → `allocate_exact_size`（遵循布局方向 + 正确推进光标，堆叠按钮不会互相重叠）。

### 教训（egui 自定义控件）
- **在 RTL / 嵌套布局里绝不要用手动 `allocate_rect` + `ui.cursor()`** —— 它忽略布局方向，会画到相邻控件上面。自定义控件一律用 `allocate_exact_size`（或直接用标准 widget + Frame），让 egui 负责排版。
- 需要"左品牌 + 右操作"时，`ui.horizontal(|ui| { 左内容; ui.with_layout(right_to_left, |ui| {...}) })` 是标准且可用的写法，嵌套 RTL 会拿到剩余宽度。

### 排查结论
- **字体加载本身没问题**：macOS 读 `/System/Library/Fonts/SFNS.ttf`（确认存在，7.9MB）作为 Proportional 首选，Noto Sans SC 作 CJK 回退；`setup_fonts`/`setup_style` 在 `main.rs:378-379` 正确调用，全仓库无其它 `set_style`/`set_visuals` 覆盖。

- **"没变化"最可能的原因**：v0.3.35 起界面已有**明显可见**变化（角色切换由单选圆点变成 NSSegmentedControl、macOS 交通灯浮在工具栏上、SF Pro 字体、新配色分层）。用户说完全没变化 → 大概率跑的是旧构建（没 `git pull` / 没重新 `cargo run` / 用的是旧 tag 打的 release 包）。**需用户确认并截图**才能继续。

### 工具教训（重要，本会话多次踩坑）
- **macOS 自带 grep 是 BSD grep，BRE 不支持 `\|` 交替**。`grep -n "a\|b"` 会**静默返回 0 匹配**，极易误判成"代码里根本没有这个符号"，本会话因此多次得出错误结论并浪费排查轮次。
- 正确写法：`grep -E "a|b"` 或 `grep -e a -e b`，或直接用 ripgrep 系的 Grep 工具（它对 `|` 处理正确）。

- **列表**：`peer_row`（36px 图标块 + 名称 + monospace 元数据 + 右侧状态/操作胶囊），替代原来的 `[复制 2 删除]` 挤一行。

### egui 踩坑（本轮新增）
- **不要用 `ui.cursor()` 定位 painter 文本**：空布局下 cursor 高度是 0，文本位置会随 egui 内部状态漂移。一律 `allocate_exact_size` 拿显式 rect 再画。
- **中英混排换行**：`text.split(' ')` 对中文永不换行（无空格）。`wrap_lines` 里按 `(c as u32) > 0x2E80` 判断 CJK，逐字断行；Latin 按空格断。
- **自定义可点击卡片**：整卡用一次 `allocate_exact_size(..., Sense::click())`，其余全用 painter 画 —— 不要在内层塞 Label widget，会和点击区抢事件。
- **`egui::Margin` 字段是 i8**（≤127），40 这种数可以但要注意别超。
- `Ui::set_clip_rect(rect)` 可安全用于把画布内容限制在分配区内。

## v0.4.4 —— 修复跨屏"只能在副机右滑、左滑即回主机"的 bug

用户反馈：鼠标能跨到 Windows 屏，但在 Windows 上**往左一滑就立刻回 Mac**，只能右滑不能左滑。

### 根因
主机的 `still_outside` 用 `冻结光标位置 + delta` 判断是否返回——而主机在 forwarding 时真实光标被冻结在共享边缘（事件被 drop），所以 `冻结位置(边缘) + 左移delta < 边缘` 恒成立，**任何一像素左移都触发返回**，与副机上光标实际位置无关。

### 修复（把"返回"决策从主机移到副机）
- **`control.rs`**：删掉 `still_outside`；`on_capture` 的 Forwarding 分支改为**无条件转发所有 delta**（只保留 `has_peer` 断连兜底：副机掉线则 `leave_forwarding`，避免光标卡死）。新增 `crossing_back(r, bbox, dx, dy)`：副机虚拟光标被推回面向主机的边缘时判定返回。`on_secondary_input` 检测到 `crossing_back` 就 `send_message(ReturnControl)`。新增 `return_control(ctx)` 供主机处理。
- **`protocol.rs`**：新增 `Message::ReturnControl`（与 Hotkey 区别：它**总是**返回主机，不轮换到下一台）。
- **`network.rs`**：新增 `Net::has_peer(name)`。
- **`main.rs`**：incoming 循环处理 `ReturnControl` → `return_control`。
- 新增 `crossing_back_*` 3 个单测 + `edge_return_roundtrip` 集成测试（走真实 TCP loopback 验证副机发 ReturnControl → 主机返回）。全套 18 测全绿。

### 关键认知
- KVM 跨屏的"返回"判断必须放在**知道光标实际位置的一方**（副机，它 clamp 自己的虚拟光标到自己的屏）。主机被 drop 事件后光标位置无意义，不能拿它做返回依据。
- 断连兜底要留：否则副机掉线时主机会一直往死 socket 转发、光标永远隐藏卡死。

## v0.4.7 —— 修复跨屏后 Mac 仍在本地滚动/点击（事件未被真正丢弃）

用户反馈：鼠标跨到 Windows 后，Mac 屏幕仍会继续滚动、点击——即同一个物理输入在 Mac 和 Windows 两边同时生效。

### 根因（关键）
`core-graphics 0.23` 的 CGEventTap 回调返回 `Option<CGEvent>`，其内部映射是：
```rust
match new_event { Some(e) => e, None => event } // None → 原事件，不是丢弃！
```
也就是说 0.23 **根本不支持丢弃事件**：返回 `None` 会被还原成原事件继续传递。所以 capture.rs 里 `if drop { None }` 的"drop"从未生效——Mac 光标/滚轮/点击一直照常接收，同时又被转发到 Windows，两边一起动。之前"跨屏后光标冻结在边缘"只是 macOS 对光标做了边缘 clamp 的假象（位置不动，但滚轮/点击这类与位置无关的事件照样漏过去）。

### 修复
- **升级 `core-graphics 0.23 → 0.25`**：0.25 起回调改返回 `CallbackResult { Keep / Drop / Replace }`，`Drop` 才会真正 `return NULL` 丢弃事件。
- **同时升级 `core-foundation 0.9 → 0.10`**：core-graphics 0.25 依赖 core-foundation 0.10，二者类型要同源（`CFRunLoopSource` / `CFMachPort`）。
- **`capture.rs`**：
  - 回调返回类型从 `Option<CGEvent>` 改为 `CallbackResult`；`None`（原"丢弃"）→ `CallbackResult::Drop`；`Some(cg_ev.clone())`（原"透传"）→ `CallbackResult::Keep`；TapDisabled 分支 `return None` → `return CallbackResult::Keep`。
  - `tap.mach_port.`（0.23 是 pub 字段）→ `tap.mach_port().`（0.25 改为方法）。
  - 导入 `CallbackResult`。

### 验证 / 兼容性说明
- `cargo check` 零错误；`cargo test` 18/18 绿（状态机逻辑未变，只有 macOS 抓取层的丢弃语义变了）。
- `kCFRunLoopCommonModes` 在 core-foundation 0.10 里通过 `pub use core_foundation_sys::runloop::*` 仍可访问，`add_source` 签名变为 `(source, CFRunLoopMode=CFStringRef)`，现有调用无需改。
- core-graphics/core-foundation 均为 `cfg(target_os="macos")` 依赖，Windows/Linux 构建不受影响。
- Cargo.lock 现在同时存在 core-graphics 0.19.2(rdev)/0.21/0.23/0.25 与 core-foundation 0.7/0.9/0.10，多版本共存无碍。

### 关键认知（务必记住）
- **core-graphics 0.23 及以下无法丢事件**：`Option<CGEvent>::None` 被 crate 映射回原事件。要做"grab 抓取/丢弃"，必须 0.25+ 的 `CallbackResult::Drop`。
- 判断 KVM 是否真的在丢弃事件，不要只看光标位置（可能只是 OS clamp 的假象），要看**滚轮/点击**这类与位置无关的事件是否也漏到本地。

## v0.4.8 —— 修复跨屏后 Windows 侧鼠标"变慢"（HiDPI 增量未归一化）

用户反馈：Mac 与 Windows 分辨率/缩放差异大，鼠标跨到 Windows 后滑动很慢。

### 根因（核心认知）
OS 上报的鼠标增量单位是**各自坐标系的单位**，不是物理像素：
- macOS `kCGMouseEventDeltaX/Y`（CGEventField 4/5）单位是 **points**。Retina @2x 下 1 point = 2 物理像素。
- Windows 声明 `PER_MONITOR_DPI_AWARE_V2` 后，`GetCursorPos` / `MOUSEEVENTF_ABSOLUTE` 都是**物理像素**，等价于 scale 1.0。

所以 Retina Mac（scale 2.0）把 100 points 原样发给 1x 的 Windows，Windows 只移动 100 物理像素——**只有应有速度的一半**。用户环境尤其明显：Mac 内置屏 1470pt（=2940 物理 px）与 Windows 3072 物理 px 宽度几乎相同，所以按物理像素归一化后，横跨两块屏的手部移动量才应该一致（原本差 2 倍）。

### 修复：转发前把增量换算到接收方坐标系
- **`protocol.rs`**：`Message::Hello` 增加 `scale: f32`（`#[serde(default = "default_hello_scale")]`，兼容旧 peer）。`MouseMotion` 文档明确为"已归一化到接收方坐标系"。
- **`layout.rs`**：新增 `Layout::scale_of(name)`、`Layout::local_scale_at(loc)`（按光标所在本地屏取 scale，多显示器不同 DPI 时正确；回退第一个本地屏）。`ensure_screen(name,w,h,is_local,scale)` 增加 scale 参数，且已存在时**刷新 w/h/scale**（peer 重连或改缩放后不会一直是旧值）。
- **`control.rs`**：`RemoteCtrl` 增加 `scale_ratio`；新增 `motion_scale_ratio(l, remote, loc) = clamp(local_scale/remote_scale, 0.25, 4.0)`，在 `enter_forwarding` 时**算一次并固定**（避免转发中途速度跳变）；`on_capture` 的 Local/Forwarding 两个分支转发前都乘该系数。diag 日志输出 scale_ratio。
- **`input.rs`**：新增 `local_scale()`，从 `LOCAL_LAYOUT` 读本机 scale。
- **`main.rs`**：`own_layout`/`hello_metrics()` 提前到建 net 之前；Hello 用本机逻辑尺寸 + scale；`ensure_screen` 传 scale。
- **`network.rs`**：hub 解析 Hello 的 scale 并注册。

### 验证
新增 `motion_scale_ratio_converts_between_scales`（含 0 scale 被 clamp 的边界）与 `hidpi_primary_doubles_forwarded_delta`（走真实 TCP loopback，验证 @2x 主机发 100 收到 200）。**20/20 全绿**。

### 坑
- 集成测试端口不能复用：`setup_hidpi_pair(19215)` 与既有 `setup_pair(19215)` 撞端口导致 `start_hub` bind 失败，改 19216。
- 给 `RemoteCtrl` 加字段要同步改测试里 5 处字面量构造。

- **Mac 两块屏都是 200%**，所以 v0.4.8 的 `scale_ratio` 恒为 2.0，不会出现"从内置屏过去快、从外接屏过去慢"的不一致。
- 三块屏物理宽度 2940 / 3840 / 3072，量级接近，按物理像素归一化后横跨行程应大体一致。
- 若用户后续反馈 Windows 上"偏快"，说明 Windows 屏物理像素密度更低（如 32" 3072 宽 ≈ 96ppi，而 4K 27" 外接 ≈ 163ppi），届时应把换算策略从"按 OS scale 因子"改为"按屏幕物理密度"。

### 概念澄清（用户问"是不是分辨率要乘以 2"）
**乘 2 的是鼠标位移增量，不是分辨率。** 分辨率/绝对坐标保持各自的逻辑值（布局与跨屏判定都在这个坐标系里，且交接用的是边的比例 fx/fy，与分辨率无关）；只有转发出去的 delta 需要从"points"换算成"物理像素"。

## v0.4.9 —— 跨屏速度系数改为「自动推导 + 手动微调」（用户要求不要写死）

用户提醒："这个乘以2可能是别的数，要程序自己判断哦。"

### 现状澄清
v0.4.8 起**就已经是程序算的**，不是硬编码：`scale_ratio = 本机 scale / 对端 scale`，2.0 只是当前环境（Mac 2.0 / Win 1.0）算出的结果。但用户的顾虑成立：**OS scale 只是"物理像素密度"的代理指标**，换显示器、Windows 改缩放、两边物理密度不同时自动值会有偏差。

### 关键推导（KVM 跨屏速度的两派目标，务必记住）
- 设 `logical_ppi = 逻辑宽 / 屏幕物理英寸`，`physical_ppi = logical_ppi × scale`。
- **物理速度一致**（同手臂行程，光标在屏上走相同英寸）：`ratio = logical_ppi_remote / logical_ppi_local`。
- **物理像素数一致**（横穿屏幕的 delta 量 ∝ 物理像素宽）：`ratio = scale_local / scale_remote` ← 我们采用的。
- 二者**仅在两台机器 physical_ppi 相同时相等**。
- 用户环境实测：Mac 内置 1470pt=2940 物理 px，Windows 3072 物理 px，宽度几乎相同 → scale 方案让"横穿两块屏的手部行程"相近（1.04 倍），正符合用户直觉；而纯物理速度方案会给出 <1 的系数，反而更慢。**没有唯一正确答案，取决于屏幕物理尺寸，而程序难以可靠获取（EDID 尺寸常不准）**。

### 实现
- `config.rs`：`motion_scale: f32`，serde default 1.0。
- `control.rs`：`MOTION_SCALE` AtomicU32（存 f32 bits）+ `set_motion_scale()` / `motion_scale()`；新增纯函数 `effective_ratio(auto, manual)`（clamp 0.1~8.0，NaN 回退 1.0），`motion_scale_ratio` 改为 `auto × manual`。**manual 是"在自动值基础上微调"而非替代**，这样换显示器后自动部分仍继续跟踪。
- `main.rs`：启动时从 config 播种。
- `app.rs`：主机分支新增「跨屏鼠标速度」卡片 —— DragValue 手动微调（0.25~4.0，改动即存盘）＋**实际换算系数实时回显**（对首台已连副机调用 `motion_scale_ratio`）。
- `i18n.rs`：card_speed / speed_multiplier / speed_hint / speed_effective / speed_no_peer 中英词条。

### 测试
新增 `manual_trim_scales_and_stays_bounded`（纯函数，避免与并发测试抢全局 `MOTION_SCALE`）。**21/21 全绿**。

### 坑
- 不要在测试里改全局 `MOTION_SCALE`：`cargo test` 并发跑，`hidpi_primary_doubles_forwarded_delta` 断言精确 2.0 会被污染 → 把可测逻辑抽成纯函数 `effective_ratio` 再测。
- app.rs 里 `control::` 需写全 `crate::control::`（该文件只 `use crate::control::GrabCtx`）。

## v0.5.0 —— 流畅度 + 剪贴板/文件互传 + 多设备多屏精确判定

用户提出三大需求：
1. **跨屏后不够丝滑/卡顿**——转发链路性能瓶颈
2. **不能互相复制文件和剪贴板共享**——arboard 只覆盖文本/图片
3. **偶尔双屏滑动 + 多个设备多屏判定**——predict_cross 用整机 bbox 导致误判

### 改动

**性能/流畅度（#31 完成）**：
- `network.rs`：所有 socket `tune()` 设 `TCP_NODELAY`（Nagle 关闭，消除 40ms 小帧合并延迟）；重写 `pump_writes` 把每条消息立即 flush（去掉 WRITE_BATCH 合并，每条 MouseMotion 独立 syscall，避免大突发挤压下一帧）。
- 主线程捕获 → `net.send_input` → sec writer 线程 → socket 的整条链路延迟从 ~40ms 降到 LAN RTT（<1ms）。

**剪贴板 + 文件互传（#32 完成）**：
- `Cargo.toml`：加 `objc = "0.2"`。
- `main.rs` 顶部 `#[cfg(target_os="macos")] #[macro_use] extern crate objc;`（`msg_send!` 宏展开依赖内部 `sel_impl!`，必须 `#[macro_use]`）。
- 新增 `src/clipfile.rs`：macOS 用 NSPasteboard `public.file-url`（NSPasteboardItem + ObjC msg_send）；Windows 用 `CF_HDROP`（DROPFILES header + 双 null 终止的 UTF-16 路径）；Linux no-op。
- 新增 `src/transfer.rs`：文件接收状态机 `Receiver { active: HashMap<token, Transfer> }`，`Transfer { root, files, current, written, expect_seq, top }`，manifest 驱动（`Message::ClipboardFiles{token, entries}` + `FileChunk{token, seq, data}` base64 分块 + `FileEnd{token}`），分块 256 KiB（≈350 KB base64），单次 copy 上限 512 MB。
- 重写 `src/clipboard.rs`：`ClipState { text, files }` 记录上次本地写入值（避免 echo loop），监控轮询 200 ms，分别独立检测文本/文件剪贴板变化，文件触发 `transfer::send_paths`（后台线程 encode+write，避免阻塞 monitor）。
- `protocol.rs`：新增 `Message::ClipboardFiles{...}`、`FileChunk{...}`、`FileEnd{...}` 三个变体；`FileEntry { path, size }` 结构。
- `app.rs`：新增 `notify(impl Into<String>)` 后台线程→GUI 的 toast 队列（GUI 轮询 + 3s 自动消失）；`i18n.rs` 新增 `tr_file_received(n)` / `tr_file_too_big()`（worker 用 `WORKER_LANG` atomic）。

**多屏精确判定（#33 完成）**：
- `control.rs::predict_cross` 彻底重写：原先用整个 local bbox 判定边缘，导致跨屏后"从远端屏的中部跨出去"或"跨到不接壤的远程屏"。改为**逐屏判定**——找到光标当前所在的 local screen，以它的边（不是 union bbox）来判定；远程屏必须 flush（≤ EDGE_ATTACH=240）接到该屏的边且 crossing axis 上 overlap 才算 hit。
- 新增 `step_local(screens, bbox, vx, vy, dx, dy)`：副机虚拟光标先尝试在当前 local 屏内 clamp，越界则用 `clamp_to_screens` 投影到最近 local 屏（多屏副机可以内部漫游）。
- 新增 2 个单测 `predict_cross_multidisplay_left_screen_to_left_remote` / `predict_cross_multidisplay_right_screen_to_right_remote` 覆盖多屏本地 + 多远程。

### 集成测试改动（关键）
- `Ctrl` 多了 `layout_snap: Arc<Layout>`，capture callback 必须 lock-free 读 layout（不能 lock layout mutex，否则在 event tap 线程里阻塞会触发 TapDisabled）。
- 集成测试 `setup_pair` / `setup_hidpi_pair` 必须 seed `layout_snap` + `local_screens`，否则 `predict_cross` 看到空 layout 返回 None → 跨不过去。
- **真正的坑**：seed `layout_snap` 时 lock `pla` 4 次（local_bbox / layout_snap / primary local_screens / secondary local_screens），而 hub reader 线程在 `handle_primary_conn` 中也会 lock layout（ensure_screen + clone snapshot）→ **race**：测试主线程与 hub reader 在 layout mutex 上抢锁。
  - 现象：在 macOS 上间歇 hang 12+ 秒，sample 显示 test thread 卡在 `__psynch_mutexwait`。
  - 解决：`setup_*_pair` 里**只 lock `local_bbox`**（最少必要），把 `layout_snap` + `local_screens` 抽出到测试自己的 `seed_layout_snap(&p, &s)` helper（每个 test 开头显式调用一次），并加 50ms `thread::sleep` 让 hub reader 完成它的 layout 操作后再 seed。
  - 注意：`setup_pair` 改了，但 `setup_hidpi_pair` 最初忘了同步改 → hidpi 测试**仍然 hang**。最终所有 lock 减到只有 `local_bbox` 才彻底稳定。

### 关键认知（务必记住）
- **core-graphics 0.23 的 `Option<CGEvent>::None` 不能丢事件**（v0.4.7 已修）。同理，`objc 0.2.x` 的 `msg_send!` 依赖内部宏 `sel_impl!`（不 `#[macro_export]`），所以 `#[macro_use] extern crate objc;` **必须放在 crate root**（即使 `#[cfg]` gate），不能只 `use objc::{class, msg_send, sel};`。
- **测试线程与 hub reader 线程在 layout mutex 上抢锁会死锁**（至少在 macOS 26 ARM64 上），race 100% 命中其中一个 setup_xxx_pair helper。**测试中涉及 TCP 的 helper 必须显式串行化所有 layout 操作**：要么用 channel 等 hub 完成，要么把 seed 推迟到 helper 返回后单独做。
- `mpsc::channel()`（unbounded）的 Sender 是 `Send + !Sync`，但 `Receiver` 是 `Send + Sync`；`send` 不会 block 在 unbounded channel 上，receiver 没启动也不会 block sender（消息进 buffer）。但在 TCP 握手 + Hello + ensure_screen 的复杂场景下，**没有显式同步点 + 多线程锁共享 = 必现 race**。

### 仍 deferred / 待用户反馈
- Linux/Windows 原生 grab 仍是 rdev observer 兜底（核心跨屏流畅度问题修不了非 macOS）。
- 文件互传目前需要 LAN 可达；Wi-Fi/防火墙仍要放行 TCP(49152)。
- 测试依赖 helper 的可重入性：未来加新集成测试要复用 `seed_layout_snap` 模式，不能直接在 setup 里 lock 多次 layout。
